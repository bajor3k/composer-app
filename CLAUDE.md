# Composer

Composer is a financial wealth management platform for advisors. It manages accounts, portfolios, CRM, compliance, and AI-assisted workflows. It runs in **demo mode**: there is no sign-in, every request acts as a fixed demo advisor, and all client data is synthetic.

## Standing rules

- **No-Gemini gate**: the app is 100% Azure for AI. `grep -rin "gemini\|generative-ai" src/ prisma/ supabase/ public/` must return nothing before every commit.
- **Shared live database**: the Supabase instance is live and shared. Do not run `db:seed` casually — it wipes and rebuilds the seeded tables. Never run `prisma migrate dev` or `prisma migrate reset` — Prisma migrate state was never initialized against this DB; schema changes go through SQL migrations applied in the Supabase SQL editor.
- **Azure-first**: the AI runs on Azure AI Foundry and the app is containerized for Azure. Keep deployment platform-agnostic (standalone output; crons are plain HTTP routes guarded by CRON_SECRET), keep `src/lib/auth.ts` as the single auth seam (a fixed demo identity now; real sign-in such as Entra ID would be added there), and keep the LLM provider seam swappable.

## Tech Stack

- **Framework**: Next.js 16.1.6 (App Router), React 19, TypeScript (strict)
- **Styling**: Tailwind CSS 4 (`@theme` in `src/app/globals.css`; no tailwind.config). 5 themes: light, dark, medium, glass, mocha.
- **Database**: Supabase (PostgreSQL) via `@supabase/supabase-js` at runtime. Prisma 7 for schema/seeding only (client generated to `src/generated/prisma`, gitignored, regenerated by `postinstall`).
- **AI**: 100% Azure. The **Composer agent** (Azure AI Foundry Agent Service, `gpt-5`) is the only model in the app. No Google dependency remains.
- **Finance**: yahoo-finance2, lightweight-charts · **Export**: ExcelJS, @react-pdf/renderer

### Composer agents (Azure AI Foundry)

Three dedicated agents, each with instructions tailored to its job. Every AI path runs
through `runAgent` in `src/lib/ai/azure-agent.ts`, which takes an `agent` key defaulting
to `"workspace"`:

| Key | Agent | Used by |
|---|---|---|
| `workspace` | Workspace Agent | workspace page, case workspace, canvas contexts, `@agent` mentions |
| `alerts` | Alerts Agent | `/api/alert-builder` — the composer's "Create alert" mode |
| `reports` | Reports Agent | `/api/report-builder` — the composer's "Create report" mode and the Report Center's "Describe in chat" |

Alerts and reports each get a **dry-run preview** before the confirm-card: the proposal
is run against live data server-side (`src/lib/alerts/preview.ts`, `src/lib/reports/preview.ts`)
so the count on the card is the evaluator's own, not the model's estimate. Both are
time-budgeted and fail soft — a preview that can't finish must never cost the user an
otherwise-good proposal. The chat also suppresses a duplicate confirm-card: asked for
something out of scope, the models answer correctly in prose but tend to re-send the
*previous* proposal to the tool alongside it.

The 48 catalog slash commands do **not** use a model at all: they execute their registry
`intent` + `defaultParams` directly via `POST /api/reports`.

Required variables are listed with placeholders in `.env.example` (`AZURE_AI_PROJECT_ENDPOINT` and the three `AZURE_AI_*_AGENT_ID`s for the agents).

- **Foundry auth is Entra-only** — the Foundry data plane rejects api-key auth with 403. `DefaultAzureCredential` covers both `az login` locally and a managed identity in Azure. If calls 401/403, run `az login` first.
- **Agent definitions live in this repo, not the portal.** Names, descriptions and instructions are declared in `src/lib/ai/foundry-agents.ts` (instructions as markdown under `src/lib/ai/instructions/`), and `npm run agents:sync` pushes them. Edit the file, not the portal — a portal edit is silently overwritten by the next sync.
- **`instructions` is optional per agent, and the workspace entry omits it.** That agent's instructions are still portal-authored and are being revised separately, so the sync payload physically cannot carry an `instructions` field for it. Foundry keeps no version history — this is what stops a stale copy from wiping the prompt behind every AI path in the app. Always `--dry` first and confirm it prints `instructions: not managed`.
- **Tool schemas live in `src/lib/ai/agent-tools.ts`** and are passed per-run, so a portal-side definition can't drift from the executors that back it. The sync sends `tools: []` on every agent to keep it that way.
- **Tool calls run pull-style**: the run pauses at `requires_action`, `azure-agent.ts` executes locally and submits outputs back. Azure never dials into the app, so no tunnel or inbound auth is needed in dev.
- **App auth is demo mode.** `getSession()` returns a constant demo identity (`user_demo` / "Demo User") and `requireAuth()` allows every request. Route handlers still call both, so real auth can be reinstated in `src/lib/auth.ts` alone. Cron routes keep `requireCronAuth` (Bearer `CRON_SECRET`).

### Live market data (`src/lib/market/`)

Every account surface renders live prices from **one** server snapshot, so the same
account cannot show different totals on different pages. Before this existed, only
`/accounts/portfolio` was live and the other five surfaces rendered stale stored scalars.

- **`GET /api/market/snapshot`** is the single endpoint all pages poll (5s). It returns
  `{ quotes, status, degraded, accounts? }`. Account totals are computed **server-side**
  (`book.ts`) so `/cash`, `/households` and `/billing` are live without loading a
  single holding row. Pages must take totals from that map, **never** by summing
  holdings client-side — that is what caused the disagreement originally.
- **`apply.ts` is the only place rounding happens** (money 2dp, price 4dp, matching the
  Decimal precisions in `prisma/schema.prisma`). One rounding site is why a roll-up and
  a drill-down cannot differ by a cent. Don't round in a page.
- **Market closed → simulated, and always labelled.** `simulate.ts` produces price as a
  *pure function* of `(symbol, anchor, sigma, quantized 5s time)` — not an accumulating
  walk. That is what makes two tabs, two pages and a server restart agree, and it bounds
  drift at `|1.35·sigma|`. Volatility is Parkinson high/low from the same Yahoo payload,
  so it costs no extra request. Simulated quotes carry `source: "simulated"`, the pill is
  **amber and spells out "Simulated"**, and `persist.ts` refuses to write them to the DB.
- **Cash/MMF symbols (`CASH`, `VMFXX`, `SPAXX`, `SWVXX`) are never simulated** and never
  carry a day change.
- **The cache never fails loudly**: entries are never deleted on error, `getSnapshot()`
  never throws, cold start hydrates from `Security`, and a Yahoo outage degrades to
  last-good values with a grey "Delayed" pill. Never surface a fetch error to the UI.
- **Scheduler**: `src/instrumentation.ts` starts it in-process for local dev (guarded on
  `NEXT_RUNTIME === "nodejs"` — it also fires on Edge, where `yahoo-finance2` cannot load —
  and on a `globalThis` singleton so HMR cannot start a second timer). The same
  `runRefreshCycle()` backs `POST /api/cron/refresh-quotes` for hosted schedulers; set
  `MARKET_SCHEDULER=off` there.
- `MARKET_REFRESH_MS` (default 30000) tunes upstream cadence. `MARKET_PERSIST=1` enables
  DB write-through — **off by default**, and note `pg` is a devDependency, so it must move
  to `dependencies` before enabling it in a standalone build.
- Pages that must **not** tick: `/trading` (execution prices), `/performance` (stored
  periods), `/retirement` (`priorYearEndBalance`), and billing's historical commissions.

`npm run db:update-prices` is still the only thing that writes real prices into the DB,
and server-side consumers (alerts evaluator, canvas context, exports) read the DB, not the
live overlay — so run it when those need to be current.

## Run Commands

```
npm run dev            # Start dev server
npm run typecheck      # tsc --noEmit (also runs as prebuild)
npx tsx scripts/market-selftest.ts   # Simulator invariants — no server/DB/network needed
npm run db:seed        # Seed database (tsx prisma/seed.ts) — SHARED DB, see standing rules
npm run db:studio      # Open Prisma Studio
npm run test           # Playwright
npm run agents:list    # What's live in Foundry right now
npm run agents:sync -- --dry     # Diff repo agent definitions against Foundry, no writes
npm run agents:sync              # Apply (add --only=alerts to scope it). Needs `az login`.
```

## Database

- **Runtime queries**: Supabase JS client. **1000-row default limit** — always paginate with `.range()` loops (`src/lib/supabase-paginate.ts`) for tables that can exceed it.
- **Views** (never DROP without recreating in the same migration; prefer CREATE OR REPLACE): portfolio_accounts, holdings_enriched, transactions_view, retirement_contributions_view, retirement_rmd_view, cash_accounts, crm_contacts, commissions. Dependency chain documented in `supabase/migrations/README.md`.
- **IDs**: CUID · **Decimals**: Currency 18,2 · Quantities 18,6 · Rates 5,4 · Returns 8,6
- When data shows as 0, null, or $NaN, check actual DB values before assuming a code bug.

## Conventions

- API routes return `NextResponse.json({ data })` or `NextResponse.json({ error }, { status })`; no streaming; no sessions (demo mode).
- All identifiers use the `composer` slug: cookies `composer_*`, localStorage `composer-*`, events `composer:*`, display name "Composer".
- Components: `"use client"` pushed as far down as possible. Tables follow the HoldingsTable pattern (`<table>`, sticky thead with opaque per-theme `<th>` backgrounds, uppercase tracking-wider headers).
- **Mocha theme coupling**: `.mocha [class~="dark:bg-[#0a0a0a]"]`-style CSS matches literal class tokens — never "clean up" arbitrary-value classes.
- Fonts: body must reference `var(--font-hanken)` directly (`--font-sans` lives in `@theme inline` and is not a real CSS var).
- UI changes: confirm WHICH page/component before editing; shared components appear on multiple pages. Pixel-level requests mean the EXACT change requested.
