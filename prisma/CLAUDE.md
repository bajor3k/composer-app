# Database (Prisma + Supabase)

## Dual Access Pattern

- **Prisma**: Schema definition + seeding only. Client generated to `src/generated/prisma` (gitignored, regenerated by `postinstall`) but NOT active at runtime.
- **Supabase JS**: All runtime queries use `@supabase/supabase-js` from `src/lib/supabase.ts`.
- **Migrations**: `supabase/migrations/0001_baseline.sql` is a snapshot of the live schema (this DB predates the repo). New schema changes are written as numbered SQL files and applied via the Supabase SQL editor. NEVER run `prisma migrate dev`/`reset` — Prisma migrate state was never initialized against this database.
- **LIVE DB**: the Supabase instance is shared and live. Do not run `db:seed` casually — it wipes and rebuilds the seeded tables.

## Schema Overview (prisma/schema.prisma)

```
User (ADMIN, ADVISOR, CLIENT, OPERATIONS)
  → Advisor (repCode, team, firmName, wealthbox sync fields)
  → Client (full KYC: address, SSN, employment, suitability, trusted contact)

Household → many Clients, many Accounts
Advisor → many Households, many Portfolios
Account (custodialPlatform, accountType, balance) → Holdings, Transactions, AccountPerformance
Portfolio → Allocations (targetPct + toleranceBand)
Security (reference pricing data) · SyncLog / SyncConfig (Wealthbox sync, dormant)
```

- Custodial platforms: `PERSHING`, `SCHWAB`, `FIDELITY`
- Account types: 15 (INDIVIDUAL, JOINT, IRA, ROTH_IRA, SEP_IRA, SIMPLE_IRA, TRUST, ESTATE, CUSTODIAL, K401, K403B, PENSION, CORPORATE, LLC, PARTNERSHIP)
- IDs: CUID · Unique: `(accountNumber, custodialPlatform)`, `(accountId, symbol)`

## Views (Supabase)

Views break silently when underlying tables are altered. Any migration touching Account, Transaction, Client, or Household MUST re-create dependent views in the same migration with `CREATE OR REPLACE VIEW` (never bare `DROP VIEW`):

- `portfolio_accounts` → Account, Client, Household, Holding, Security, Advisor, Portfolio
- `holdings_enriched` → Holding, Security
- `transactions_view` → Transaction, Account
- `retirement_contributions_view` / `retirement_rmd_view` → Account, Client, Household, Transaction
- `cash_accounts` → Account, Holding
- `crm_contacts`, `commissions` → CRM/billing aggregations
  - ⚠️ **`crm_contacts` is the advisor roster** (a view over `User` + `Advisor`, ~10 rows), NOT client data. Client CRM data is the **`Client` table** (360 rows) — that's what `/communication/crm` reads. Its `tech_stack`/`calls`/`tickets` columns call `random()` *inside the view definition*, so they return different values on every read: never display them or join/paginate on them.
  - `Client` carries PII (`ssn`, `idNumber`). Leave those out of the `select` list rather than fetching and hiding them client-side.

## Seeding (prisma/seed.ts)

1 firm → 5 advisors → 60 households → 300 accounts (spread across all 3 custodians) → ~3K holdings → ~7.5K transactions + model portfolios and operations staff (see `CONFIG` at the top of seed.ts — some inline comments there are stale). Uses `pg` via PgBouncer pooler (`DATABASE_URL`), `max: 1` connection. Feature tables are seeded against real accounts via `seedFeatureTables()` — reseeds must keep FK integrity (Ticket→User is RESTRICT).

- Supabase returns max 1000 rows per query — paginate with `.range()` batches when reading seeded volumes.
